# Архитектура прототипа

Рабочий документ для задач с кодом. Правила, обязательные для кода, лежат в [CLAUDE.md](../CLAUDE.md); здесь — как это устроено и с чего начинать. Всё, что помечено «предложение Claude», — стартовый вариант: Core-чат показывает его в плане, и команда подтверждает или меняет. Числа стартовые и живут в `game/data/`, а не в коде.

## 1. Словарь

| Термин | Что это |
| --- | --- |
| **t** | время игрока: всегда растёт, игрока не откатывает ничто |
| **τ (тик мира)** | позиция мира на его истории: целое число физических тиков; в обычном режиме растёт, при удержании Shift убывает |
| **тик** | один шаг `_physics_process`; 60 в секунду |
| **кадр истории** | словарь «id объекта → его состояние» на одном тике мира |
| **история** | последовательность кадров комнаты (буфер ограниченной длины) |
| **голова истории** | самый новый записанный кадр |
| **курсор** | тик мира, в котором мир сейчас показан; совпадает с головой в обычном режиме и уходит в прошлое при Shift |
| **предыстория (prelude)** | история, записанная до того, как игрок взял управление: уровень «прогоняют» без игрока, чтобы было что откатывать |
| **ветка** | продолжение истории после вмешательства игрока: всё, что записано правее курсора, отбрасывается |
| **временной объект** | объект комнаты, чьё состояние записывается и воспроизводится: дверь, платформа, вода, кнопка, рычаг, ящик |
| **точка взаимодействия** | место, где игрок действует: кнопка, рычаг, клапан; толкать объекты нельзя |
| **комната** | один уровень или его часть со своей историей |
| **живой источник** | объект вне истории: игрок и обратные предметы; действует по текущему моменту, а не по кадру (раздел 2.5) |
| **обратный предмет** | живой источник с обращённой анимацией и поведением «наоборот»: без Shift необычный, при Shift обычный; флаг на объекте, не второе поле времени |
| **зона дерева** | записанный участок, который можно поджечь и потушить: целая → горит → сгорела |

## 2. Модель времени (предложение Claude)

Главная идея: **воспроизведение вместо пересчёта**. В обратном режиме и при повторном проходе вперёд объекты не симулируются заново, а получают состояние из записанного кадра. Симуляция идёт только на голове истории. Из этого вытекает ветвление «само по себе».

Каждый физический тик комнаты:

1. **Shift зажат** и курсор больше начала истории: `cursor -= 1`, все объекты получают `restore_state(frame[cursor])`.
2. **Shift зажат**, курсор в начале истории: мир стоит на месте (закреплён на кадре 0), игрок действует сколько нужно. Это основа безопасных уровней: решение не требует угадывать тайминг.
3. **Shift отпущен**, курсор левее головы: `cursor += 1`, воспроизводится записанное будущее. Так и задумано (решение команды 8.11.2026, вариант «А»): шестерня, которую игрок повернул раньше, повернётся сама, вода потечёт снова, а прошлое меняет только вмешательство.
4. **Shift отпущен**, курсор на голове: объекты делают `simulate_tick()`, затем в историю записывается новый кадр.
5. **Вмешательство** игрока (кнопка, рычаг, клапан) или живого источника (обратный предмет, раздел 2.5) при курсоре левее головы: изменённое состояние записывается в кадр курсора, всё, что правее, отбрасывается (`branch()`), и с этого места симуляция идёт заново. Это и есть новая ветка.
6. **Игрок в историю не входит**: его позиция, скорость и инвентарь не записываются.

Следствия, которые нужно проверить тестами:

- вмешательство в обратном режиме не возвращается при дальнейшем откате: объект подчиняется тем кадрам, что левее;
- без вмешательства записанное будущее проигрывается целиком: перемотали назад, отпустили, и шестерня повернулась сама (вариант «А»);
- два раза подряд назад и вперёд без вмешательства не меняют мир (детерминизм);
- после вмешательства старое будущее никогда больше не воспроизводится.

### 2.1. Частота записи

Предложение Claude: **писать кадр на каждом физическом тике (60 в секунду)** и хранить 20 секунд на комнату. Для 10–30 объектов это порядка 1200 кадров по несколько чисел на объект, меньше мегабайта. Плюс: нет интерполяции, воспроизведение точное, тест непрерывности простой (шаг между соседними кадрами не больше порога). Минус: больше данных, чем в концепции (там 10–20 снимков в секунду с интерполяцией). Если профилировка покажет проблему, переходим на запись раз в N тиков (стартовое запасное значение — каждый 4-й тик, 15 в секунду) с интерполяцией числовых полей; логические значения (открыто/закрыто) берутся из ближайшего прошлого кадра. Это запасной вариант из списка урезания в [roadmap.md](roadmap.md).

### 2.2. Предыстория

Для уровней, которые начинаются со следствия, у игрока должно быть что откатывать. Поэтому перед стартом уровня `TimeWorld` без игрока «прогоняет» комнату `prelude_seconds` секунд и записывает кадры; игрок появляется в конце предыстории. Тогда Shift ведёт игрока вглубь того, что произошло до него: дверь закрывается, вода уходит, рука-манипулятор дёргает рычаг, и это можно увидеть и переиграть.

- Длина предыстории задаётся в данных уровня и не больше длины истории (20 с).
- Начало предыстории — кадр 0; там мир закреплён, пока зажат Shift.
- **Где число (2.6):** `RoomTime` ищет в `levels.json` запись, у которой `scene` — сцена комнаты, и берёт её `prelude_seconds`; нет записи (комната открыта сама по себе, тестовая сцена) — `default_prelude_seconds` из `time.json`. В сцене числа нет. Сброс комнаты прогоняет ту же предысторию заново.
- **Скриптованные события** — поле `prelude_events` той же записи, список в порядке данных: `{"second": 1, "press": "valve"}` нажимает точку взаимодействия, как игрок (рычаг со всеми целями); `{"second": 1, "id": "lamp", "state": {...}}` ставит поля состояния объекта (манипулятор, запечённый обратный предмет). Секунда переводится в тик; событие на тике k меняет кадр k после начала предыстории, событие на секунде 0 — стартовый кадр. Предыстория идёт на голове, поэтому событие — обычная запись, не ветка; при перемотке оно откатывается, при отпускании Shift проигрывается из записи (правило «А»). Код: `TimeWorld.run_prelude(objects, ticks, events)` и `TimeWorld.prelude_events_from_data()`.
- Скриптованные события (кто и когда дёрнул рычаг) задаются в данных или в сцене, а не случайно: уровень обязан проигрываться одинаково.

### 2.3. Столкновение с игроком (решение 8.11.2026)

**8.11.2026 (D30, D31):** мир двигает героя: платформа, идущая назад, везёт его, ящик, летящий назад, толкает. Замирание мира, описанное ниже, остаётся только для случая, когда следующий кадр раздавил бы героя. То, что герой держит, остаётся с ним при перемотке.

Если при воспроизведении следующий кадр поставит твёрдый временной объект на место игрока, **мир замирает на этом тике**: курсор не двигается, пока игрок не отойдёт. Это проще, чем замирание отдельного объекта, и совпадает с «одно время на комнату» (T0.1). Каждый твёрдый объект отвечает на вопрос `blocks_player_at(state, player_rect) -> bool`. Игрока объекты не давят. Запас `carry_margin_px` (`objects.json`) общий для платформы и двери: ноги героя могут заходить в твёрдый объект на эту глубину, и это «едет», а не «раздавлен». Поэтому дверь, поднимающаяся под ногами, везёт героя вверх, а не замораживает мир (баг 11.11.2026); дверь, опускающаяся на голову, или стена сбоку по-прежнему давят.

### 2.4. Окна действия

Все окна, в которых игрок должен успеть что-то сделать, не короче **3 секунд**, и их границы видны. Паузы на траектории объекта («платформа стоит у края 4 с») закладываются в данные. Решение, зависящее от секундного тайминга, — ошибка уровня.

### 2.5. Живые источники (решение 8.11.2026; детали подтверждены 8.11.2026)

Игрок и обратные предметы не пишутся в кадры. В каждый тик они смотрят на текущее направление времени и своё положение (см. [concept.md](concept.md), раздел 2.3).

1. **На игрока** живой источник действует вживую в обоих режимах: батут подбрасывает, огонь жжёт, конвейер везёт. Таймеры, которые действуют на игрока (сгорание за 3 с), идут по времени игрока `t`, а не мира.
2. **На записанный объект на голове истории** действие — обычная запись состояния.
3. **На записанный объект левее головы** действие — то же вмешательство, что и у игрока (пункт 5 выше): `TimeWorld.live_action(object_id, new_state)` пишет состояние в кадр курсора и вызывает `branch()`. Путь один и для игрока, и для обратных предметов.
4. Пока Shift зажат, а живой источник продолжает действовать, курсор идёт назад, и каждый тик контакта переписывает кадр под курсором. При отпускании остаётся последнее записанное состояние, курсор равен голове, и мир дальше симулируется. Чтобы не обрезать комнату на каждом тике, реализация может применять эффект один раз за контакт; для игрока итог одинаков (открытый вопрос 7 в концепции).
5. События по расписанию (рука дёргает рычаг на 10-й секунде) зависят от времени мира `τ` и состояния, а не от записи, поэтому после ветки они продолжают происходить: `simulate_tick` обязан быть детерминированным.
6. **Запекание:** в части уровней поведение обратного предмета записывается как скриптовое событие предыстории (`prelude`). В кадры оно попадает как обычное, и игрок видит его при перемотке.

**Пример: обратный огнемёт и дерево.** Без Shift огнемёт всасывает огонь (в обычное время он гасит). При зажатом Shift он выпускает огонь и поджигает зону дерева: `live_action(tree_3, {state: BURNING, since_tick: cursor})`, то есть зона получает эффект огня. Сам огонь не обратный: счёт `burn_seconds` (стартовое значение 3, число живёт в `game/data/`) идёт только в `simulate_tick` на голове, значит, зона догорит до «сгорела» только после отпускания Shift.

**Обратный предмет — вещь (решение команды 13.11.2026, задача 2.7).** Игрок находит предмет в комнате, подбирает и бросает его клавишей E (если ближе рычаг или кнопка, срабатывают они), стреляет, держа F. У предмета две половины:

- **Тело записывается**, как всё, кроме игрока (`objects/reverse_flamethrower.gd`, группы `temporal`, `live`, `carried`): лежащий предмет падает на голове истории, под Shift идёт назад по своим кадрам. В руках он с игроком и кадры не берёт (правило «что игрок держит, остаётся с ним»). Подобрать и бросить — вмешательство игрока (`player_action`). Бросок ещё и переписывает прошлое предмета: во всех кадрах левее курсора он лежит там, где его отпустили (`TimeWorld.rewrite_past`, `Timeline.rewrite_past`). Иначе предмет, который игрок пронёс через перемотанное время, прыгал бы в старое место; так под Shift он стоит, как мир на кадре 0, и после отпускания падает.
- **Огонь живой и не записывается.** `RoomTime` после каждого тика зовёт `act(room, direction)` у узлов группы `live`. Струя действует через `live_action` только на зону, которая ещё не в нужном состоянии, — это и есть «раз за контакт». Под Shift курсор каждый тик уходит назад, поэтому зона поджигается заново на каждом кадре касания и остаётся гореть после отпускания. Смена направления времени глушит струю, пока F не нажмут снова: иначе отпущенный Shift с зажатой F сразу потушил бы только что зажжённое. Если отпустить F раньше Shift, дальнейшая перемотка покажет зону целой, а повтор зажжёт её на том же кадре (правило «А»).

**Огонь (задача 2.7).** Зона дерева (`objects/wood_zone.gd`, правила — `core/wood_burn.gd`) твёрдая, пока целая или горит; сгоревшая — проход. Горение считается только в `simulate_tick`. Вода, накрывшая горящую зону, тушит её на голове; потушенная зона снова целая и может гореть ещё раз. При тушении (водой или огнемётом) в кадр пишется номер кадра `doused`, и пар рисуется из времени мира (группа `world_clock`): под Shift он оседает обратно в дерево. Игрок в пламени (зона и `flame_px` над ней, `flame_side_px` по бокам) набирает жар (`core/scorch.gd`) по своему времени при любом направлении; через `fire_seconds` он сгорает, комната сбрасывается; вне огня жар спадает за `fire_cool_seconds`. Вид огня (2.7А) — украшение: `core/fire_look.gd` считает его из времени мира и записанного состояния (`phase`, `burn`, `burnt`, `doused`), шейдеры дерева и пламени берут те же числа, поэтому вид на одном кадре одинаков вперёд и назад.

**Побочный эффект.** Если живой источник действует, когда курсор стоит на кадре 0, ветка отбрасывает всю предысторию. В карточках уровней обратный предмет не ставят так, чтобы он стирал причину, которую игрок должен увидеть.

## 3. Структура проекта

```
game/
  project.godot
  autoload/        # узлы-синглтоны: time_manager.gd, game_data.gd
  core/            # RefCounted без узлов: timeline.gd, temporal_recorder.gd, time_world.gd, content.gd, level_data.gd, input_log.gd
  objects/         # временные объекты и игрок: player.tscn/.gd, platform_moving, door, button, lever, water, water_float, crate
  levels/          # test_room.tscn, level_01.tscn … level_10.tscn, room_time.gd
  ui/              # HUD, устройство на руке, меню
  data/            # time.json, player.json, objects.json, levels.json, texts.json
  art/             # backgrounds, decals, characters, objects, ui, particles
  audio/
  tests/           # test_runner.gd, script_errors.gd, test_core.gd, ui_smoke_test.gd, solutions/
```

`core/` не наследует `Node` (правило из [CLAUDE.md](../CLAUDE.md)). Всё, что должно быть узлом-синглтоном, лежит в `autoload/`.

## 4. Компоненты

| Компонент | Где | Что делает |
| --- | --- | --- |
| `TimeManager` (autoload, `Node`) | `autoload/time_manager.gd` | читает действие `rewind`; хранит направление `+1` или `−1`; сигнал `direction_changed(direction: int)`; сам ничего не записывает |
| `Timeline` (`RefCounted`) | `core/timeline.gd` | кадры, курсор, голова, кольцевой буфер; `record(frame)`, `step_back()`, `step_forward()`, `branch()`, `at_head()`, `at_start()` |
| `TimeWorld` (`RefCounted`) | `core/time_world.gd` | правила раздела 2: `tick(direction, objects, player_rect)` двигает курсор, проигрывает или записывает кадр; `run_prelude()`; `player_action()` и `live_action()`; решает «мир ждёт из-за игрока» (2.3). Объекты получает аргументом на каждом вызове |
| `RoomTime` (`Node`, в каждой сцене уровня) | `levels/room_time.gd` | прямой потомок комнаты; на каждом тике берёт направление у `TimeManager`, объекты группы `temporal` и прямоугольник игрока и зовёт `TimeWorld.tick()`; передаёт объектам смену направления; `reset()` для сброса уровня |
| временной объект | `objects/*` | уникальный `object_id`; методы `capture_state() -> Dictionary`, `restore_state(state: Dictionary)`, `simulate_tick(tick: int)`; `blocks_player_at(...)` для твёрдых |
| `InteractionSystem` | `objects/player.gd` и точки взаимодействия | игрок жмёт `interact` рядом с точкой; точка вызывает `TimeWorld.player_action(object_id, new_state)`, тот делает `branch()` при необходимости |
| `Player` (`CharacterBody2D`) | `objects/player.tscn` | управление не зависит от направления времени; ездит на платформах |
| `LevelController` | `levels/` | загрузка, сброс по `reset_level`, переход к следующему уровню, выход |
| `LevelLoader` (автозагрузка) | `autoload/level_loader.gd` | `load_level(id)` по `levels.json`, `go_to_list()`, `current_id`; действие `back_to_list` (Backspace) возвращает из уровня в список `ui/level_select.tscn` — главную сцену; новая сцена стартует в прямом времени |
| живой объект (обратные предметы) | `objects/*` | группа `live`, не `temporal`: нет `capture_state`; в каждый тик либо действует на игрока, либо зовёт `TimeWorld.live_action(...)` (раздел 2.5) |

Временные объекты узнаются по группе `temporal` и по набору методов (утиная типизация), потому что платформа и дверь наследуют `AnimatableBody2D`, а кнопка — `Area2D`, и общий базовый класс невозможен. Тест проверяет, что каждый узел группы имеет все нужные методы.

Платформы и двери — `AnimatableBody2D` с включённым `sync_to_physics`, положение задаёт `restore_state` или `simulate_tick`: тогда `CharacterBody2D` игрока едет вместе с ними и в обычном, и в обратном режиме.

### 4.1. Контракт временного объекта (задача 1.4, 8.11.2026)

Общего базового класса нет: дверь и платформа — `AnimatableBody2D`, кнопка будет `Area2D`. Объект — это сцена в `game/objects/`, корень которой стоит в группе `temporal` (группа задаётся в `.tscn`) и умеет следующее. Образцы — `objects/door.gd` и `objects/platform.gd`.

| Что | Зачем | Правило |
| --- | --- | --- |
| `@export var object_id: String` | ключ объекта в кадре | уникален в комнате; пустой или повторный — ошибка `TemporalRecorder.validate()` и теста |
| `capture_state() -> Dictionary` | состояние для кадра | только простые типы (`int`, `bool`, `float`, `Vector2`), числа целыми, где можно (раздел 5); всё, без чего объект не восстановится, включая фазу своего цикла; берёт значения из своих переменных, а не из `position` тела с `sync_to_physics` (физика возвращает его с опозданием на шаг, а `capture_state()` зовут и между тиками — при вмешательстве; ошибка платформы, 13.11.2026) |
| `restore_state(state)` | показать кадр | ставит всё из `state`, в том числе положение узла; ничего не симулирует; `capture_state()` сразу после него возвращает тот же словарь |
| `simulate_tick(tick)` | один тик на голове истории | только здесь объект живёт сам; результат зависит только от своего состояния и данных (детерминизм); `tick` — номер нового кадра |
| `on_time_direction_changed(direction)` | смена направления, `+1` или `−1` | для вида и звука (частицы, анимация механизма); состояние не меняет |
| `blocks_player_at(state, player_rect) -> bool` | правило «не давить» (2.3) | `true`, если объект в состоянии `state` залез бы в тело игрока; прямоугольники в координатах комнаты; пустой `player_rect` — всегда `false`. У нетвёрдых объектов (кнопка) просто `return false` |

Ещё правила:

- Числа поведения (скорость, паузы, длительности) — в `game/data/objects.json`, по разделу на вид объекта; проверка в `Content.validate_objects()`: окна действия не короче 3 с, шаг за тик не больше `max_state_step`. Геометрия (куда едет, на сколько поднимается) — `@export` в сцене уровня.
- Положение в сцене — исходное (дверь ставят закрытой, платформу в начальной точке); объект запоминает его до первого изменения.
- Объект не хранит ссылок на комнату, `RoomTime` или игрока; изменить записанный объект извне можно только через `RoomTime.player_action(object_id, new_state)` или `live_action(...)`.
- Что проверяют тесты (`tests/test_objects.gd`, `tests/test_time_world.gd`): у каждого узла группы `temporal` в комнате есть все методы и уникальный `object_id`; обратный путь повторяет записанный кадр в кадр, соседние кадры отличаются не больше чем на `max_state_step`; на кадре 0 мир стоит; отпущенный Shift проигрывает то же будущее без симуляции; вмешательство отрезает будущее; мир ждёт, а не давит игрока; игрок едет на платформе в обе стороны.

## 5. Что записывается

Только простые типы (`float`, `int`, `bool`, `Vector2`), числа целыми там, где возможно (JSON и сравнения в тестах не любят дроби).

| Объект | Состояние |
| --- | --- |
| подвижная платформа | `phase` (целое, тик на траектории), `position` |
| дверь | `open` (0…1000, тысячные доли), `locked` |
| кнопка | `pressed`, `since_tick` |
| рычаг | `on` |
| вода | `level` (0…10000: мельче двери, чтобы время слива из данных выдерживалось с точностью до процента), `flow` (−1, 0, +1) и `powered` (источник открыт); поток считается в `simulate_tick` из `powered`, который ставит источник (рычаг-вентиль, позже шестерня) через свои цели, а не живёт сам по себе. Поплавки (`WaterFloat`, дети воды) своего состояния не имеют: высота считается из `level` |
| ящик | `position`, `velocity` (когда появится) |
| манипулятор и прочие скриптовые механизмы | `phase` |
| шестерня | `angle` (тысячные доли оборота), `turned` |
| зона дерева | `state` (0 целая, 1 горит, 2 сгорела), `since_tick` |
| лампа | `lit`, `broken` |

## 6. Данные

Числа лежат в `game/data/`, правятся без кода, и тест проверяет их (`Content.validate()` по аналогии с Crown).

`time.json`:

```json
{
  "physics_ticks_per_second": 60,
  "snapshot_every_ticks": 1,
  "history_seconds": 20,
  "default_prelude_seconds": 0,
  "max_state_step": 40
}
```

`player.json` (стартовые значения, на сетке 64 px и экране 1920×1080):

```json
{
  "walk_speed": 360,
  "acceleration": 2400,
  "friction": 3000,
  "gravity": 2200,
  "jump_velocity": 780,
  "max_fall_speed": 1200,
  "coyote_seconds": 0.08,
  "jump_buffer_seconds": 0.1
}
```

Прыжок при них около 140 px, то есть чуть больше двух клеток, поэтому ступени и платформы в блокауте кратны 64 px и не выше двух клеток.

`objects.json`: поведение временных объектов: `door` (`open_seconds`, `hold_open_seconds`, `close_seconds`, `hold_closed_seconds`), `platform` (`speed` в px/с, `pause_seconds`), `carry_margin_px` — на сколько пикселей ноги игрока могут уйти в платформу, чтобы это считалось «едет», а не «давит». Скорость платформы за тик должна быть меньше `carry_margin_px`.

`levels.json`: список уровней в порядке прохождения: `id`, `scene`, `prelude_seconds`, `title` и необязательный `prelude_events` (раздел 2.2); проверка — `Content.validate_levels`, а тест `test_every_prelude_event_names_an_object_of_its_room` проверяет, что событие называет объект своей комнаты.

## 8. Тесты

Ошибка скрипта в тесте или в игре валит этот тест (для этого есть `tests/script_errors.gd` — логгер ошибок). Команды те же, что в [CLAUDE.md](../CLAUDE.md).

## 11. Вопросы к плану кода

1. Запись на каждом тике (предложение) или раз в 4 тика с интерполяцией.
2. Замирание всего мира при столкновении (предложение) или одного объекта.
3. Как именно проигрывать скриптованную предысторию: симуляцией `simulate_tick()` с отключённым игроком (предложение) или записанным файлом кадров.
4. Нужен ли отдельный класс `Branch` или хватает метода `Timeline.branch()`; в концепции есть `BranchManager`, в разделе 2 он сведён к одному вызову. **8.11.2026:** отдельного класса нет, хватает `Timeline.branch()` через `TimeWorld` (раздел 2).

6. Размер уровня: один экран 1920×1080 или комнаты шире с камерой, следящей за игроком. **8.11.2026:** один экран.
